01The problem

Software already moves money. Nobody checks what it is about to do.

AI agents now hold wallets, pay invoices and rebalance treasuries. Payment networks are adding agent identities and signed mandates, which prove who asked. None of them proves that a policy was evaluated against the state the money was about to leave.

The losses of the last two years share that shape.

02Where it sits

A gate between whatever decides and wherever money moves.

Decision-makers send intents down. PALISADE judges each one against the ledger and your policy, then either executes it or refuses it. A certificate comes back either way.

DecidesAI agents, trading strategies, people, schedulersAnything that can produce an intent: pay, transfer or convert.
intentcertificate
JudgesPALISADEKernel checks, your policy, unforgeable proofs, a hash-chained ledger and a signed certificate for every decision.
executionevents
MovesBank accounts, cards, stablecoins, tokenized depositsAdapters carry intents to the rails. The kernel itself does no network IO.

Start read-only

Shadow mode replays your existing payment history and says what it would have blocked. Nothing in your stack changes.

Test before you publish

Backtest a new policy against last quarter's real payments and compare it with the one you run today.

Replay any decision

The ledger is a fold over an append-only log, so any past state and any past decision can be rebuilt exactly.

03The gate

Your rules, in a language that refuses to guess.

Policies are short files. Money carries its currency in its type, arithmetic is exact, and a rule that compares dollars with euros does not load. Every rule reports what it observed and what it required.

hardened.palexcerpt

set agent_merchants = {"openai", "anthropic", "aws", "api-market"}
set sanctioned      = {"ofac:garantex", "ofac:lazarus-1"}

policy "agent-usdc" currency USDC {
  require  "not sanctioned":         counterparty not in sanctioned
  require  "allowlisted merchant":   counterparty in agent_merchants
  require  "per-payment cap":        amount <= 500 USDC
  require  "daily agent budget":     total_outflow(24h) + amount <= 2000 USDC
  require  "never drain the wallet": amount <= 0.25 * balance
  require  "no duplicate payments":  duplicates(10m) == 0
  require  "burst limit":            count(1m) < 5
  law      "agent daily budget":     total_outflow(24h) <= 2000 USDC
}
ALLOWexit 0

Every check passed. The payment is committed and the log grows by one entry.

ESCALATEexit 3

An escalate rule fired. A named person can approve it; nobody can approve a denial.

DENYexit 2

A check failed. Nothing moves, and the refusal is recorded with its reasons.

Before your rules, every intent passes four kernel checks

  • well-formedPositive amount, distinct endpoints, a valid rate for conversions.
  • knownThe source is your account. Payments go out, transfers stay in.
  • freshThe intent id has never executed and its time is not before the ledger's. Retries and backdating fail here.
  • fundedOnly settled money counts. Inside the kernel, spending a deposit that is still pending is a type error.

A typo in currency is caught at load time

t.pal:3:28: this policy is for USD but the literal is in EUR; PALISADE never converts currencies implicitly

The typechecker reports the file, line and column, and suggests the fix when it can, for example writing 250 USD where a bare number was compared with money.

Proofs can't be forged. Each check returns a proof value that only the checker can create. Code outside the library cannot construct one.

Proofs name what they cover. A proof about one payment, in one ledger state, cannot authorize another payment or a newer state. Both are compile errors.

Laws are checked, not assumed. Property tests check the kernel's own laws. The stress tester checks yours. PALISADE does not claim the whole system is formally verified.

04Evidence

Every decision leaves a certificate you can re-derive.

A certificate names the intent, the exact ledger state it was judged against, the policy's hash, every check and the verdict. It contains no clock reading and no randomness, so replaying the log with the same policy reproduces it byte for byte. That is what palisade audit does.

    05Tested against attacks

    It attacks your policy before someone else does.

    A policy file can state laws: things that must hold in every state, such as "daily outflow stays under 15% of assets." The stress tester generates sequences shaped like real incidents: amounts one minor unit under each threshold, bursts at one timestamp, retries, new payees, spending against pending deposits. It checks every law after every step and shrinks each failure to a short reproduction.

    The naive policy below caps single payments and states the daily law. Its rules don't guarantee it.

    random sequence, 23 steps
    shrunk counterexample, 2 steps
    T+00:00:00   pay treasury -> new-vendor  250000.00 USD   => allow
T+00:00:00   pay treasury -> attacker-2   62500.00 USD   => allow
violated at step 2: total_outflow(24h) = 312500.00 USD; required <= 307500.00 USD

    Its USDC budget broke too: five payments built from amounts one minor unit under the cap overshot 2,000 USDC by 0.000003. Exact arithmetic is why that shows up at all. The hardened policy held all 8 laws across 17,000 generated sequences.

    RunIt yourself

    Everything above comes from one script.

    You need GHC 9.6 and cabal 3.10 or later. The demo takes under half a minute and runs every scene in the terminal at the top of this page. The test suite has 65 examples, most of them property tests.

    git clone https://github.com/saintparish4/palisade
cd palisade
cabal build
bash scenarios/demo/run-demo.sh
